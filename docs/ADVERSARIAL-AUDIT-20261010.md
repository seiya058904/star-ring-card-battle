## 3. 确认问题与修复

### A01 — P1：结算把读取失败或无效存档当作空档覆盖

**位置：** `js/fixed-game-rules.js` 的最终 `uiRenderer.showResult` / `commitCampaignResult`；`js/campaign-mode.js` 的读取与重置路径。
**置信度：0.99。** P1 按已有进度和历史记录被覆盖的影响评级；触发条件并非常规每局都会出现。

**触发状态与原结果：** 预先保存罗林福第五关完成、revision 42 和历史记录；丽莎娅完成第一关时令 `getItem` 抛错而 `setItem` 可写。
原代码捕获读取异常后返回默认进度，随后成功写入 revision 1，罗林福退回第一关且历史被替换，无错误提示。
损坏 JSON 和未知 `version: 2` 也经宽容的展示读取器变成默认档并被结算覆盖。
普通浏览器权限拒绝常常同时拒绝读写；选择性读取失败属于故障注入，坏 JSON/未知格式则另有独立复现。

**修复：** 新增 `campaignMode.readProgressForWrite(storage, characters)`，将“展示可以容错”和“写入必须确认原数据可识别”分开。
只有 `getItem` 明确返回 `null` 才当作新档；读取失败、JSON 错误、未知版本、错误根结构、字符数组及非法/溢出的 revision 或 resetGeneration 均拒绝写入。
旧 v1 存档缺少并发计数字段仍按 0 兼容；对已识别 v1 内容继续沿用原规范化，不新增格式或迁移机制。
结果保存和重置共用该严格读取器，锁内完成读取、代际比较和写入。

**回归：** `verify-campaign-result-storage-errors.mjs`、原并发/重置套件、浏览器坏 JSON 和读取异常场景。
错误时原始字符串逐字节保留、零成功写入；有效档保留其他角色记录，revision 42 → 43。

### A02 — P2：结果页忽略 Web Locks 的拒绝或同步异常

**位置：** `js/fixed-game-rules.js` 最终 `uiRenderer.showResult` 调用 `campaignMode.commitProgress` 的边界。
**置信度：0.99。**

**原结果：** `navigator.locks.request` 返回拒绝的 Promise 时，页面照常展示胜利，零写入、零失败提示，并产生未处理 rejection。
同步抛错还可能打断结果后续展示。

**修复：** 用同步 `try/catch` 加 Promise rejection handler 统一处理存储/锁异常。
显示“战役进度保存失败，本局结果未写入本地存档。”，继续展示结果；结果页的一次性标志仍在申请锁前设置。
没有把“已渲染结果”误认为“已经保存”，也没有增加自动重试、额外领取或重复写入入口。

**回归：** 同步 throw、异步 reject、排队后读取/写入抛错、重复 `showResult`、新战斗开始后旧请求拒绝。
Node 和浏览器均观察到一次失败提示、原档保留、无未处理 rejection。

### A03 — P2：路线弹窗中取消的选择污染结果页重试/下一关

**位置：** `js/campaign-ui.js` 注册的 `global.campaignResultActions` 按钮闭包。
**置信度：0.99。**

**真实 UI 复现：** 丽莎娅/普通难度第一关结算 → 返回战役路线 → 选择罗林福/困难 → 取消 → 重试本关。
原来只恢复关卡，保留路线弹窗改过的共享角色/难度，实际进入罗林福/困难。
同样的共享变量也影响“下一关”。

**修复：** 重试/续关先从这次结果捕获的 `state.campaign` 恢复角色和难度，再计算对应关卡，最后走原 `startCampaign` 授权入口。
用户主动从路线点击“进入”仍采用新选择；重置或未解锁导致的关卡拒绝仍有效。

**回归：** 新 Node 套件 7/7；同套件运行于输入基线时失败。
浏览器用可见按钮完成上述路径，重试得到丽莎娅/普通/第一关，下一关得到丽莎娅/普通/第二关。
只有进入结果的敌方 HP=0 边界是测试注入，后续路径均是真实交互。

### A04 — P2：持续伤害/召唤协击绕过普通人族、神人低血量天赋

**位置：** `js/fixed-game-rules.js` 的 `applyCard`、`tickStatuses` 和召唤协击路径。
**置信度：0.98。**

**原结果：** 相同目标降到 35% 以下，直接卡牌在整张结算末尾触发一次“均衡意志”，DOT 或协击却不触发；后续无关卡牌可能才补触发。
已使用现有“纵火Ⅶ”制造燃烧，验证该差异并非虚构伤害种类。

**修复：** 提取 `gameEngine.triggerBalancedWill`，保留原 8% 治疗、8% 护盾、一次性标志和丽莎娅战役专属被动排除。
卡牌仍在整张结算末尾调用；DOT/协击只在实际 HP 变化且结算后目标仍存活时补调用。

**死亡边界：** 首次整合实现漏掉存活条件，确实被两个原门禁抓到“致命 DOT 后错误恢复 8%”回归。
没有改旧断言或调数值，而是在两条新路径增加 `hp > 0`，并补九项致命/显式复生边界用例。
无显式复生的致命 DOT/协击保持死亡；显式复生先在 `resolveDamage` 消费，再检查存活与阈值。
原卡牌整张末尾的既有致命恢复语义保持，不能把新共享 helper 的存在解释成非卡牌伤害获得复生能力。

**回归：** 人族/神人 × 卡牌/DOT/协击、护盾完全吸收、目标不受伤、丽莎娅不叠加普通天赋、无复生死亡、显式复生消费和统计。
独立审计还验证 20% 低血复生后可触发一次普通天赋、50% 复生不触发。

### A05 — P2：DOT 净化了禁锢，但旧快照仍保留行动锁或执行已删除状态

**位置：** `js/fixed-game-rules.js` 的 `tickStatuses`，经 `campaign-runtime.js` 注册的生命变化 hook 进入净化/被动/Boss阶段检查。
**置信度：0.99。**

**现有卡牌组合：** 丽莎娅对第五关 Boss，先被“统治Ⅲ”禁锢，再受到“黑暗吞噬Ⅵ”的诅咒。
回合开始遍历到禁锢后，后续 DOT 触发胜利圣仪并净化该禁锢，但旧 `skipAction` 仍为 true；状态图标消失而本回合不能行动。
若 hook 移除了还没遍历的状态，旧 `statuses.slice()` 也可能继续执行它。

**修复：** 每次快照迭代先确认该对象仍在当前状态数组中；所有 DOT/hook 完成后、持续时间递减之前，从剩余禁锢重新计算行动限制。
自然到期的禁锢此刻仍存在，因此本回合照常跳过并产生原有控制抗性；净化移除与自然到期不混为一谈。

**回归：** 禁锢位于 DOT 前/后、已净化的后续 DOT、丽莎娅/Boss净化、自然到期、显式复生后净化。
修复撤销的变异检查会重新出现 `skipAction: true` 失败。

### A06 — P2：守卫已经分摊伤害，最终结果却没有守卫事件

**位置：** `js/fixed-game-rules.js` 的 `resolveDamage` → `applyCard` 的 `result.summonGuard` → 根 HTML 的 `effectsRenderer.play` / `showSummonGuardDamage`。
**置信度：0.99。**

**原结果：** 分摊逻辑已扣除召唤物 HP，日志和总伤害正确，但 `resolveDamage` 没返回内部已有的 `guard`，下游 `settlement.guard` 永远为空，守卫伤害反馈缺失。
这不是伤害公式错误，而是有效覆写层遗漏了已有 UI 所需的结算元数据。

**修复：** 返回 `guard: shared.guard || null`，无有效结算时返回空元数据。
没有第二次扣血、重新计算分摊或增加新的动画机制。

**回归：** 守卫存活/被击破、全护盾吸收、主人复生、总实际伤害守恒。
Chromium 中用“沙王领主Ⅲ”建立守卫，设为一血并清空主人护盾，真实回合获得可支付攻击后点击出牌：
守卫移除，但收到恰好一次 `amount: 1` 的守卫事件，实际 `.summon-float-text.guard` 节点存在。
